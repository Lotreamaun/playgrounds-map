## Context

Сейчас фронтенд показывает только карту: `App.tsx` хранит `courts`, `MapView.tsx` отображает их маркерами, данные берутся через `getCourts(bbox)` в `frontend/src/services/api.ts` (поле адреса `address` появится в change `court-address`). Бэкенд `GET /courts` уже принимает все параметры bbox как необязательные (`Optional[float]`), поэтому запрос без bbox вернёт все площадки без изменения сервера (см. proposal.md — Why).

## Goals / Non-Goals

**Goals:**
- Переключатель режимов «карта / список»
- Список площадок с адресом, покрытием и состоянием
- Клиентская сортировка «ближайшие» по геолокации пользователя (Haversine)
- Клик по строке списка — центрирование карты на площадке

**Non-Goals:**
- Новые backend-эндпоинты (ближайшие считаются клиентом по загруженным данным)
- Поиск по тексту/фильтры по виду спорта или покрытию — вне рамок этого change
- Геокодирование и правка адреса (это из change `court-address`)
- Пагинация списка — для MVP (один город) весь набор загружается разом

## Decisions

### Переключатель вида живёт в `App.tsx`, глобальное состояние поднимается наверх
`App.tsx` хранит `view: 'map' | 'list'` и `selectedCourt: Court | null`. Переключатель рендерит либо `MapView`, либо новый `CourtList`. Это даёт единый источник истины для «клик по строке → показать на карте».
- **Альтернатива**: состояние внутри компонентов — отклонено, т.к. выбор в списке должен влиять на карту и наоборот; нужен общий стейт.

### Загрузка всех площадок — необязательный bbox в `getCourts`
Расширяем `getCourts` в `frontend/src/services/api.ts`: параметр bbox становится необязательным. При его отсутствии параметры не добавляются в query string, и сервер возвращает все площадки. Существующие вызовы с bbox не меняются.
- **Альтернатива**: отдельная функция `getAllCourts` — отклонено, чтобы не плодить дубли; один endpoint, один клиентский метод.

### Список использует тот же срез данных, что и карта
`CourtList` получает `courts` из `App.tsx`. Переключение вида не перезагружает данные: список наполняется из уже загруженного набора (а при входе в список при необходимости догружается полный набор). Это упрощает синхронизацию и не тратит лишние запросы.
- **Альтернатива**: отдельный fetch при каждом переключении — избыточно, так как площадок в одном городе немного.

### Сортировка «по близости» — клиентская, через Haversine utility
Расчёт расстояния выполняется на клиенте в небольшой утилите (`distanceHaversine(lat1, lon1, lat2, lon2)`). Список сортирует площадки по возрастанию расстояния от координат пользователя.
- **Альтернатива A**: backend-эндпоинт `/courts/nearby` — отклонено: сервер уже отдаёт все площадки, вычисление на клиенте избавляет от лишнего API и сетевых задержек, данные не секретны.
- **Альтернатива B**: геолокация в утилите не нужна — отклонено, ключевое «найти ближайшую ко мне» без геолокации невозможно.

### Поведение без геолокации — понятный фолбэк
Если геолокация отклонена/недоступна, сортировка «по близости» не работает. Решение: не показывать точные расстояния и оставить список в порядке по умолчанию (например, по id/имени), но дать пользователю понять, что геолокация не разрешена (без раздражающего брейк-экспериента). Это согласуется со spec-сценарием «Nearest sort without geolocation».
- **Альтернатива**: по умолчанию завернуть в Тбилиси — отклонено, т.к. это не «моя близость», а надо честно показать отсутствие геоданных.

### Выбор в списке → централизованный `selectedCourt` → карта
Клик по строке списка устанавливает `selectedCourt` в `App.tsx`. `MapView` получает его как проп и при монтировании/переключении вида центрирует карту на его координаты и открывает его карточку (переиспользуя popup из `CourtMarker.tsx`/`CourtCard`).
- **Альтернатива**: строки списка хранят собственный обработчик без связи с картой — отклонено, это сломает требование «click row focuses court on map».

## Risks / Trade-offs

- [Список загружает весь набор и может расти] → Для одного города это приемлемо; при масштабировании введём пагинацию/фильтры (вне рамок).
- [Зависимость от change `court-address` (поле `address`)] → Порядок внедрения: сначала `court-address`, затем этот change; список корректно обрабатывает площадки без адреса (заглушка).
- [Центрирование карты при переключении вида] → Механика «ref/центрировать после рендера» потребует аккуратной работы с экземпляром карты; реализуется через существующий `setLocation`/кам-интерфейс `MapView`.
- [Геолокация пользователя уже использовалась для стартового центрирования] → переиспользуем тот же паттерн `navigator.geolocation`; стоит избегать повторного запроса прав без надобности (фолбэк при отказе).

## Migration Plan

1. Расширить `getCourts` (необязательный bbox) — обратная совместимость сохраняется
2. Добавить Haversine-утилиту и компонент `CourtList`
3. Поднять `view`/`selectedCourt` в `App.tsx`, подключить переключатель и связь список ↔ карта
4. Деструктивных изменений нет; откат — убрать переключатель, вернуть только карту
