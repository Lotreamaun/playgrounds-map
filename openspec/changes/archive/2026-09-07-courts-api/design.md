## Context

Опирается на `backend-foundation`: `Settings` (в т.ч. `ADMIN_TOKEN`), синхронная DB-сессия и модель `Court` уже существуют. Требования и мотивация — в `proposal.md` и `specs/courts/spec.md`. SQLite не поддерживает геозапросы, поэтому дедупликация по расстоянию считается в Python (см. `vision.md` §2).

## Goals / Non-Goals

**Goals:**
- Полный CRUD по площадкам поверх фундамента из `backend-foundation`, без изменений в нём
- Идемпотентное создание (дедуп по координатам) и защита фото-аплоада, как in `vision.md` §5, §2

**Non-Goals:**
- Аутентификация/полноценная модерация — только `ADMIN_TOKEN`-проверка для `DELETE`, как временный предохранитель v1 (см. roadmap v1.2)
- Гео-индексация/PostGIS — на MVP допустим полный перебор + Haversine в Python, объём данных мал (один город)
- Rate-limiting — не требуется на MVP согласно `vision.md` (`slowapi` заявлен как «опционально»)

## Decisions

- **Дедупликация — полный перебор + Haversine в Python, а не SQL-геозапрос**: SQLite не имеет встроенных геофункций; при объёме MVP (один город, один вид спорта на старте) перебор по таблице `courts` того же `sport_type` не является узким местом. Пересмотр — при переходе на PostgreSQL/PostGIS (v2+, см. `vision.md` §10).
- **Порядок проверок в `POST /courts`**: сначала валидация координат/обязательных полей (422), затем дедуп по расстоянию (409), затем валидация и сохранение фото (400) — от дешёвых и синхронных проверок к более затратным (запись на диск), чтобы не сохранять файл до того, как остальные проверки пройдены.
- **Фото хранится на диске (volume), а не в БД**: путь сохраняется в `photo_url`; согласуется с `vision.md` §7 (volume для SQLite и фото в деплое).
- **`DELETE` защищён простым сравнением токена из заголовка/параметра с `ADMIN_TOKEN`** — не полноценная auth-система, осознанный минимальный барьер для v1 (см. `vision.md` §4, п.5).

## Risks / Trade-offs

- [Полный перебор для дедупа] → приемлемо на объёме MVP; при росте числа площадок в городе может понадобиться индекс по `sport_type` (уже неявно есть через фильтрацию перед Haversine-подсчётом).
- [`ADMIN_TOKEN` в виде общего секрета, не персональной авторизации] → соответствует явному решению `vision.md` не делать модерацию до v1.2; риск компрометации одного токена = удаление любой площадки, смягчается тем, что данные не критичны для MVP одного города.
- [Фото на локальном volume, не в объектном хранилище] → соответствует `vision.md` §7 (Dockhost + volume); миграция на S3-совместимое хранилище — будущий шаг, не в рамках MVP.
