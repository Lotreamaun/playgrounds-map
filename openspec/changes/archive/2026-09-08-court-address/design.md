## Context

Сейчас у модели `Court` (`backend/app/models/court.py`) нет отдельного поля адреса — в карточке (`CourtMarker.tsx`) показывается `description` с fallback на строку "Address unavailable". Данные хранятся в SQLite (`backend/data/courtmap.db`), таблицы создаются через `SQLModel.metadata.create_all` при старте (см. proposal.md — Why). Форма добавления (`CourtForm.tsx`) пока не имеет поля адреса и не вызывает геокодер.

## Goals / Non-Goals

**Goals:**
- Добавить поле `address` в модель Court, принимать/возвращать его в API
- Не потерять существующие данные при обновлении схемы
- Автоматически подставлять адрес по координатам клика (Яндекс Геокодер) с ручной правкой
- Показывать адрес в карточке площадки

**Non-Goals:**
- Полноценная система версионирования схемы (Alembic) — используем лёгкую миграцию, см. Decisions
- Геокодирование на бэкенде — принято решение, что геокодер живёт на фронте
- Заполнение адресов для уже существующих записей (ретроактивный backfill)
- Автоопределение адреса без клика по карте

## Decisions

### Поле `address` — необязательное, nullable
`address: Optional[str] = None` в `CourtBase`. Не делаем обязательным: существующие записи и создание без адреса не должны ломаться. Форма предлагает адрес, но не требует.
- **Альтернатива**: обязательное с дефолтом `""` — отклонено, т.к. создаёт мусорные значения и осложняет тесты.

### Миграция БД — лёгкий идемпотентный ALTER при старте
Учитывая масштаб MVP (один город, SQLite), не вводим Alembic. В `create_db_and_tables()` после `create_all` добавляем проверку наличия столбца `address` в `courts` и, при отсутствии, выполняем `ALTER TABLE courts ADD COLUMN address VARCHAR`. Операция идемпотентна и безопасна для существующей `courtmap.db`.
- **Альтернатива A**: Alembic — избыточен для MVP, добавляет конфигурацию и алхимическое дерево, которых сейчас нет.
- **Альтернатива B**: сброс БД — теряет пользовательские данные, неприемлемо.
- **Риск**: дублируется логика между моделью SQLModel и ручным DDL; на практике столбец добавляется один раз, далее схема стабильна.

### Геокодер — вызов на фронте, механизм по доступности JS API
Обратное геокодирование выполняется на клиенте. Точный способ вызова зависит от того, что доступно в загружаемой v3 SDK и ключе (`VITE_YANDEX_MAPS_KEY`): встроенный модуль геокодера либо HTTP-запрос к Геокодер API (например, `geocoder-api.yandex.ru` / соответствующий эндпоинт v3) с тем же ключом. Выбор конкретного механизма фиксируется в коде после проверки в рантайме; поведение для пользователя не меняется (адрес подставляется в поле формы).
- **Альтернатива**: геокодирование на бэкенде — отклонено (принятое решение), т.к. выносит секрет/лимиты ключа на сервер и добавляет зависимость.
- **Следствие**: лимит бесплатного тарифа Геокодера расходуется на клиенте; для формы с автоподстановкой этого достаточно.

### Кэш геокодирования в рамках сессии
Форма кэширует соответствие `координаты → адрес` в памяти (Map) на время жизни сессии, чтобы повторный клик в ту же точку не дёргал геокодер повторно.
- **Альтернатива**: без кэша — лишние запросы к API; кэш тривиален, потому включаем.

### Карточка — показ `address`, заглушка на русском
`CourtMarker.tsx` переключается с `description` на `address`. При отсутствии адреса показывается осмысленная русская заглушка (например, "Адрес не указан"), а не техническое сообщение. Перевод прочих строк интерфейса выносится в отдельный change `russian-interface` — здесь фиксируем только заглушку адреса.

## Risks / Trade-offs

- [Несоответствие DDL и модели SQLModel] → Миграция выполняется один раз идемпотентно; тест на старте после миграции подтверждает наличие столбца.
- [Геокодер v3 недоступен через тот же механизм, что v2] → Спроектировано как слой-обёртка; конкретный механизм (SDK-модуль или HTTP) выбирается на этапе реализации после проверки, поведение не меняется.
- [Изменение OpenAPI → ручные типы `src/types/court.ts`] → Регенерация через `npm run types:court` с запущенным backend; поле `address` появится в типах без правки вручную.
- [Ретроактивный backfill исключён] → Существующие площадки останутся без адреса до повторного редактирования; приемлемо для MVP.

## Migration Plan

1. Добавить `address` в `CourtBase`
2. Расширить `create_db_and_tables()` идемпотентным ALTER (проверка + `ADD COLUMN`)
3. Обновить `POST /courts` (приём `address`), типы фронта регенерировать
4. Бэкенд-миграция применится автоматически при следующем старте; откат — удалить столбец вручную (не требуется для MVP)

## Open Questions

- Точный программный интерфейс Геокодера в загружаемой v3 SDK (модуль vs HTTP-запрос) — уточняется на этапе реализации, не влияет на спеки и разбивку задач.
