## Context

См. `proposal.md` — Why. Текущее состояние кода, влияющее на дизайн:

- **Бэкенд хранит runtime-данные по путям относительно рабочей директории**: `DATABASE_URL=sqlite:///./data/courtmap.db`, фото — `data/photos/`; статика монтируется как `StaticFiles(directory="data/photos")` (`backend/app/main.py:40`), что падает на отсутствующей директории.
- **`photo_url` в БД относительный** (`/photos/{filename}`) — значит, фото должно отдаваться с того же origin, что и приложение, либо путь придётся переписывать/перерабатывать.
- **Фронтенд формирует запросы из `VITE_API_BASE_URL`** (`frontend/src/services/api.ts:3`), который вшивается при сборке; пустая строка делает запросы относительными. Публичные ключи Яндекса (`VITE_YANDEX_MAPS_KEY`, `VITE_YANDEX_GEOCODER_KEY`) тоже вшиваются при сборке.
- **Документация уже зафиксировала топологию**: `vision.md` §7 и `PLAN.md` этап 4 (4.1–4.4) — отдельный Nginx-контейнер для фронтенда и контейнер FastAPI, SQLite на volume, целевая платформа Dockhost.

## Goals / Non-Goals

**Goals:**
- Контейнеризация обоих частей: `backend/Dockerfile` и `frontend/Dockerfile` (multi-stage: сборка Vite → nginx).
- Прод-топология именно для Dockhost: два контейнера в одном проекте (общение по имени сервиса), один домен, постоянный сетевой диск.
- Локальная воспроизводимая проверка топологии через `docker compose up`.
- Бэкенд обязан стартовать на пустом volume (создание `data/` и `data/photos/` при старте).
- `dockhost.yaml` как декларативный манифест проекта (билды, контейнеры, volume, домен+маршрут).

**Non-Goals:**
- CDN для статики (возможное будущее расширение).
- Миграция SQLite → PostgreSQL/PostGIS (v2+).
- Мульти-воркер/мульти-реплика backend под SQLite.
- HTTPS-терминация — её берёт на себя платформа Dockhost (домен + Let's Encrypt).
- `docker-compose.yml` как манифест для Dockhost — платформа использует `dockhost.yaml`; compose нужен только для локального прогона.

## Decisions

### 1. Топология: два контейнера в одном проекте Dockhost

```
Домен ── маршрут "/" ──► frontend:80 (nginx)
                             │ /courts /photos /health /docs /openapi.json
                             ▼ proxy_pass
                        backend:8000 (uvicorn)
                             │
                        volume: /app/data (SQLite + photos)
```

- **Почему**: соответствует зафиксированной в документации архитектуре (`vision.md` §7 — «свой Nginx-контейнер»); nginx даёт правильные кэш-заголовки для хешированных ассетов и открывает путь к CDN.
- **Альтернатива**: один контейнер — FastAPI раздаёт `dist/`. Меньше инфраструктуры, но ломает задокументированную архитектуру, смешивает serving с прикладным кодом, кэш-заголовки пришлось бы настраивать вручную. Отклонено.
- **Следствие**: имя `backend` в `nginx.conf` (`proxy_pass http://backend:8000`) должно совпадать с именем контейнера в `dockhost.yaml`.

### 2. Один origin без API-поддомена

Фронтенд и API живут на одном домене; nginx проксирует только API/фото/health-пути на backend.

- **Почему**: относительный `photo_url` из БД работает без изменений; не нужны CORS в проде; не нужен второй домен.
- **Альтернатива**: `api.<domain>` → потребовался бы абсолютный `photo_url` (миграция/перезапись в БД) и CORS. Отклонено как избыточное для MVP.

### 3. Прод-сборка фронтенда: same-origin API base

`VITE_API_BASE_URL=""` для продакшена — фронтенд ходит на свой origin. В `frontend/Dockerfile` значение задаётся как `ARG` с дефолтом. Ключи Яндекса — тоже `ARG` (публичные, ограничение у Яндекса по домену Referer, а не по секретности).

### 4. Распространение build-time `VITE_*` в сборке

- В `frontend/Dockerfile`: `ARG VITE_YANDEX_MAPS_KEY`, `ARG VITE_YANDEX_GEOCODER_KEY`, `ARG VITE_API_BASE_URL=""`, затем `ENV` тех же переменных на build-этапе.
- Значения по умолчанию подтягиваются из закоммиченного `frontend/.env.production` (публичные ключи — не секрет). Если панель Dockhost умеет передавать build-args при сборке из репозитория — значения задаются там и переопределяют дефолты.
- **Альтернатива**: передавать сборке `--build-arg` через CI. Для MVP нет CI — отклонено.

### 5. Старт backend на пустом volume

В `backend/app/main.py` перед `StaticFiles`-монтированием создать `data/` и `data/photos/` (`Path("data").mkdir(parents=True, exist_ok=True)` и подкаталог photos). Это же чинит старт SQLite на свежем диске (nginx: parent-директория БД).

### 6. Один сетевой диск на весь runtime

Named volume смонтирован в `/app/data` (покрывает и `courtmap.db`, и `photos/`). `DATABASE_URL` остаётся `sqlite:///./data/courtmap.db` — при `WORKDIR /app` путь резолвится в том. Раздельные диски через `subPath` — не нужны для MVP.

### 7. Одиночный процесс и пины зависимостей

- Backend запускается одним uvicorn-процессом без `--workers` (SQLite — single-writer); `replicas: 1` в `dockhost.yaml`.
- Версии в `backend/requirements.txt` зафиксировать `==` (сейчас диапазоны) и сгенерировать lock-файл/зафиксировать транс-зависимости — воспроизводимые сборки.

### 8. `docker-compose.yml` — только локальная проверка

Зеркалит прод-структуру (frontend:80 + backend:8000 + named volume), чтобы прогнать image-сборку и маршрутизацию локально до контакта с Dockhost. Не используется платформой.

## Risks / Trade-offs

- **`StaticFiles` хрупок к порядку создания директорий** → стартовый mkdir (решение 5) и healthcheck `GET /health` как канарейка.
- **Несколько реплик backend сломают SQLite** (file locking) → `replicas: 1`, документально в `dockhost.yaml`.
- **Имя `backend` зашито в nginx** → держать одинаковым в `nginx.conf` и `dockhost.yaml`; различие = молчаливые 502 после редеплоя.
- **Домен не добавлен в allowed referers у ключей Яндекса → карта не грузится** → шаг оператора: прописать прод-домен в консоли Яндекса до публичного релиза.
- **Dockhost может не поддерживать build-args при сборке из репозитория** → fallback: закоммиченный `.env.production` с публичными ключами; изменение ключа = коммит + пересборка (приемлемо для MVP).
- **Права на volume при non-root пользователе в контейнере** → либо Dockhost `uid`/`gid` в конфиге контейнера, либо для MVP оставить root и зафиксировать как технический долг.
- **Пути относительно CWD** → строго фиксированный `WORKDIR /app` в `backend/Dockerfile`; комментарий у `DATABASE_URL` и монтирования статики.

## Migration Plan

- **Развёртывание**: `docker compose up --build` локально для проверки → подключить репозиторий и `dockhost.yaml` в проекте Dockhost → задать переменные окружения (`ADMIN_TOKEN`, `CORS_ORIGINS`) и build-time значения → создать домен и маршрут → проверить `/health`, карту, добавление площадки и фото.
- **Откат**: Push-to-Deploy пересборка на предыдущий коммит; данные на volume не затрагиваются; при желании — снапшот диска до первого деплоя со сделанными записями.
- **Данные**: миграций схемы нет; при первом запуске таблицы создаются автоматически.
