## Context

Сегодня `App.tsx` хранит режим добавления (`addMode`) и выбранную точку (`pick: Coordinates | null`) отдельно от карты: `MapView` не знает о `pick` и ничего не рисует для него. Вход в режим добавления (`handleAddToggle`) на desktop сразу открывает `CourtForm` в боковой панели с `coordinates=null`; на мобильном форма не открывается вовсе — вместо неё показываются cancel-FAB и текстовая подсказка, пока пользователь не тапнет по карте. Клик по карте в режиме добавления (`MapView.handleMapClick` → `onMapClick`) — единственный путь, которым `pick` получает значение; он же и должен остаться единственным путём **ручной** коррекции точки. См. proposal.md - Why/What Changes для мотивации и общего описания.

## Goals / Non-Goals

**Goals:**
- Получать `pick` из `navigator.geolocation.getCurrentPosition` сразу при включении `addMode`, без нового отдельного UI-режима «определение точки».
- Не терять существующий ручной путь (клик по карте) — он остаётся и как способ скорректировать авто-точку, и как единственный путь при отказе геолокации.
- Сделать `pick` видимым на карте, раз он теперь может появляться без явного клика пользователя.

**Non-Goals:**
- Перетаскивание (drag) маркера точки мышью/пальцем — вне рамок, коррекция только повторным кликом/тапом.
- Изменение самого геокодера или контракта `POST /courts`.
- Фоновое отслеживание позиции (`watchPosition`) — точка фиксируется один раз при входе в режим добавления.

## Decisions

**Где инициировать запрос геолокации.** В `App.tsx:handleAddToggle`, а не в `MapView`: `MapView` уже делает свой независимый запрос геолокации при монтировании (центрирование карты), и это не тот же запрос — у него другая цель (центр карты, не точка добавления) и другой момент срабатывания. Смешивать их в одном вызове усложнило бы оба сценария без выгоды; два независимых `getCurrentPosition` — самый простой вариант.

**Опции запроса.** `enableHighAccuracy: true` (точность важна — площадку нужно указать с точностью до объекта), `timeout: 8000` (обосновывает требование «Geolocation timeout» — не более ~8с ожидания перед откатом на ручной ввод), `maximumAge: 30000` — если у браузера уже есть недавний фикс (например, только что использованный для центрирования карты), это позволяет ответить мгновенно вместо повторного аппаратного опроса.

**Защита от гонки при отмене.** Пока `getCurrentPosition` ожидает ответ, пользователь может успеть нажать «Отмена» (`handleCancelAdd`) или снова тумблернуть кнопку. Колбэки успеха/ошибки должны проверять актуальность запроса (например, сравнивая с `addModeRef.current` и/или локальным флагом-токеном запроса) перед тем, как применять результат к состоянию — иначе поздно пришедшая геопозиция может неожиданно открыть форму после того, как пользователь уже отменил добавление.

**Видимый маркер точки (`pick`).** `pick` становится пропом `MapView`, рендерится как дополнительный `YMapMarker` поверх слоя площадок — визуально отличимый от `CourtMarker` (например, акцентный цвет/иконка «черновика», без спортивной иконки). Это не часть кластеризации (`YMapClusterer`) — маркер один, кластер по одному объекту не нужен, поэтому он рендерится отдельным `YMapMarker` вне `YMapClusterer`, аналогично тому, как уже существуют элементы вне слоя `courts`.

**Единая точка входа для desktop и mobile.** Сейчас поведение `handleAddToggle` расходится по платформам (`if (!isMobile) setSheet({ type: 'form' })`). После этого изменения расхождение по времени открытия формы исчезает: на обеих платформах форма открывается сразу, как только `pick` определён (геолокацией — сразу же после успешного ответа; вручную — как и сегодня, по клику карты). До получения ответа геолокации UI остаётся в «pending»-состоянии (спиннер/текст на кнопке или FAB), не открывая форму преждевременно с пустыми координатами.

**Fallback переиспользует существующий ручной UI.** При ошибке/таймауте/отсутствии `navigator.geolocation` состояние совпадает с сегодняшним «addMode без pick»: на desktop форма с пустыми координатами и плейсхолдером, на мобильном — cancel-FAB и подсказка «Нажмите на карту». Новый код не создаёт для этого случая отдельный UI, а просто не переопределяет `pick` и позволяет существующей логике сработать как раньше.

## Risks / Trade-offs

- [Двойной запрос геолокации (центрирование карты + добавление точки) может дважды показать пользователю системный permission-prompt, если браузер не кеширует решение] → Большинство браузеров запоминают выбор пользователя (allow/deny) на источник на время сессии/постоянно, второй вызов `getCurrentPosition` не показывает повторный prompt; если браузер всё же спросит дважды, это не ломает сценарий — просто требует второго клика «Разрешить».
- [Точность геолокации по Wi-Fi/IP на десктопе может быть низкой (сотни метров — километры), и авто-точка окажется не на самой площадке] → Явный видимый маркер + сохранённая возможность кликнуть по карте для коррекции — пользователь всегда видит и может поправить точку перед отправкой; это уже часть требований, не дополнительная работа.
- [`maximumAge` может вернуть устаревший кэш, если пользователь физически переместился между загрузкой карты и нажатием «Добавить»] → 30с — короткое окно, риск невелик; при сомнении пользователь просто кликает по карте, чтобы уточнить точку.
